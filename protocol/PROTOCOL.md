# Протокол RemoteDesk — v1 (этап M0)

Связь между приложением на телефоне («клиент») и агентом на ПК («агент»).

## Транспорт
- **WebSocket поверх TLS** (`wss://<ip>:<port>/ws`), порт по умолчанию **47800** (настраивается в агенте).
- Сертификат агента самоподписанный (ECDSA P-256), создаётся при первом запуске и хранится в `%APPDATA%\RemoteDesk\agent.pfx`.
- Клиент **закрепляет** сертификат: принимает соединение, только если SHA-256 от DER-сертификата совпадает с отпечатком, полученным при сопряжении (`fp`). Имя хоста не проверяется — проверяется только отпечаток.
- Сообщения управления — текстовые кадры JSON (UTF-8). Поле `t` — тип сообщения. Для частых событий ввода (этап M1) появятся бинарные кадры.

## Поиск в сети (mDNS / DNS-SD)
Агент объявляет службу **`_rdesk._tcp.local`** на своём порту. TXT-записи:

| Ключ | Значение |
|---|---|
| `v` | версия протокола (`1`) |
| `id` | идентификатор агента (UUID без дефисов) |
| `name` | имя компьютера |
| `fp` | отпечаток сертификата (base64url без `=`) |

Клиент по `id` узнаёт уже сопряжённые компьютеры и обновляет их IP-адрес. Новый компьютер из mDNS можно сопрячь только кодом (см. ниже) — отпечаток из mDNS сам по себе не доверенный.

## Сопряжение

### По QR-коду (основной способ)
Агент показывает QR-код со ссылкой:
```
rdesk://pair?v=1&id=<agentId>&n=<имя ПК>&h=<ip1,ip2>&p=<порт>&fp=<отпечаток>&k=<ключ>
```
- `h` — все IPv4-адреса ПК в локальных сетях, `k` — одноразовый ключ сопряжения (16 случайных байт, base64url), живёт 10 минут и обновляется после каждого успешного сопряжения.
- Клиент подключается к любому адресу из `h` с закреплённым `fp` и шлёт `pair` с `secret = k`.
- QR-код передаёт отпечаток по «оптическому каналу», поэтому подменить агента в сети нельзя.

### По 6-значному коду (запасной способ)
- Агент показывает код `123456` (живёт 5 минут), клиент находит ПК через mDNS и шлёт `pair` с `secret = "123456"`.
- После 5 неверных попыток подряд код сбрасывается, новый — через кнопку в агенте.
- Отпечаток в этом случае пришёл из mDNS. Чтобы исключить подмену, обе стороны после сопряжения показывают **4 слова-проверки**, вычисленные из отпечатка; пользователь сверяет их глазами. (Этап M1, в M0 — только QR.)

### Обмен
```
клиент → {"t":"pair","secret":"…","deviceId":"…","deviceName":"Pixel 8","platform":"android","appVersion":"0.1.0"}
агент  → {"t":"paired","token":"…","agent":{…AgentInfo}}
```
`token` — 32 случайных байта (base64url), постоянный пароль этого телефона. Агент хранит только SHA-256 от токена. Клиент хранит токен вместе с `id`, `fp` и адресами агента.

## Подключение сопряжённого телефона
```
клиент → {"t":"hello","deviceId":"…","token":"…","appVersion":"0.1.0"}
агент  → {"t":"welcome","agent":{…AgentInfo},"permissions":["input","power","files","clipboard","screen"]}
```
Пока не прошли `pair` или `hello`, агент принимает только эти два сообщения; на остальные отвечает `error` `not_authenticated` и закрывает соединение.

### AgentInfo
```json
{
  "id": "…", "name": "DESKTOP-ABC123", "os": "Windows 11 Pro 26200",
  "version": "0.1.0", "protocol": 1,
  "macs": [{"mac": "AA:BB:CC:DD:EE:FF", "name": "Ethernet", "ip": "192.168.0.102", "wired": true}]
}
```
`macs` нужны клиенту для Wake-on-LAN — пользователю не придётся вводить MAC вручную.

## Служебные сообщения
| t | Направление | Поля | Смысл |
|---|---|---|---|
| `ping` | клиент → агент | `n` (число) | Проверка связи, раз в 5 с |
| `pong` | агент → клиент | `n` | Ответ с тем же `n`; клиент считает задержку |
| `error` | агент → клиент | `code`, `msg` | Ошибка. Коды: `bad_secret`, `secret_expired`, `too_many_attempts`, `not_authenticated`, `revoked`, `bad_message`, `unsupported_version` |
| `bye` | обе стороны | `reason?` | Вежливое закрытие |

Неизвестные поля игнорируются, неизвестный `t` → `error` `bad_message` (соединение не рвётся). Так старый клиент работает с новым агентом.

## Отзыв доступа
В агенте пользователь удаляет телефон из списка → его токен стирается, текущее соединение закрывается с `error` `revoked`. Клиент помечает компьютер «доступ отозван» и предлагает сопрячь заново.
